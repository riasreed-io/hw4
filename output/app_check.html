Three checks against the running site, with every claim verified against the database.

How this was run
Backend: cd backend && uvicorn main:app --reload --port 8000. Front end: npm --prefix frontend run dev on http://localhost:5180. Every screenshot below is from that running site. Under each one, the numbers the site showed are checked against campus_customs.db directly.

Check 1

The chat reports real inventory and real prices

Asked "what inventory do you have for hoodie?", the assistant answered with a count, six named products with prices, and the range of stock totals. None of those numbers come from the model — it called search_products, and every figure below was read out of the database.

The "27" is worth noting on its own. The raw garment_type column holds 22 different spellings of about six categories, so matching it literally would have returned 5 hoodies. The backend normalises it first, which is why the count is right.

Check 2

A category question fills the page with product cards

The same hoodie question did not just answer in the chat bubble — the page itself rendered the matching products as full cards under the heading Hoodies. This is the API contract from Problem 7: the agent returns structured product ids, and the front end renders them.

What this proves
The heading reads HoodiesThe agent chose that label itself, in the shopper's words.
Cards show $45, $45, $68 and stock badgesEvery field was rebuilt from the database after the agent chose the ids — the model never supplies a price.
Cards are the same component as the catalogue gridClicking one opens the full product page, exactly like a card found by browsing.
Check 3

Usability feature: the filter bar

The products page used to offer one way to narrow 102 items — six garment chips. It now filters on five facets at once, each with a live count, and the whole filter state lives in the URL so a narrowed grid can be shared or bookmarked.
